## Overview

- **專案類型**：Prototype／Personal Project。公司、客戶與產品皆為模擬資料，不代表任何真實客戶。
- **情境**：一家 B2B 工業零件經銷商，客戶以 Email 寄送詢價與採購需求。
- **負責範圍**：需求分析、系統設計、全端開發、部署，以及擷取品質評估。
- **Live Demo**：<https://orderflow-agent.vercel.app>（登入時選擇業務或主管身分）
- **原始碼**：<https://github.com/gkfat/orderflow-agent>

## Business Problem

- 業務助理要逐封閱讀詢價信，查產品主檔與價目表後，手動輸入報價單草稿，再交主管核准。
- 料號、數量、交期在轉錄時容易出錯，常常到核准階段才被發現。
- 轉寄、重送的信件可能被處理兩次，產生重複的報價。
- 最低訂購量、價格底線、交期等規則靠個人經驗判斷，標準不一致。
- 多位業務共用同一個系統時，客戶歸屬不清，容易互相看到或搶走彼此的客戶與訂單。

> 以上為情境設定，非實際訪談或量測結果。

## Discovery

- **利害關係人**：客戶（寄信）、業務（負責自己的客戶）、業務主管（核准報價、指派客戶、設定規則）
- **需求與限制**：
  - AI 不能取代必要的業務規則；建立正式交易前一定要人員確認
  - 同一封信不能產生兩張報價單
  - 業務只能看到並處理自己負責的客戶
  - 每一步都要能追查是誰在何時做了什麼
- **成功指標**：擷取欄位正確率、Schema 通過率、人工修正率、重複交易數為 0
- **不在本次範圍**：真實 ERP／CRM 串接、真實信箱收信、LINE 入口、多租戶與計費

## Proposed Solution

**LLM 只負責把非結構化的信件轉成固定欄位；能不能成單，由程式規則與人決定。**

### 考慮過但沒有採用的做法

- **純 Rule-based 解析**：詢價信格式自由（表格、口語、英文、回覆串），規則寫不完，維護成本高。
- **讓 Agent 自主呼叫工具直接建單**：高風險操作（建立報價）交給模型自行決定，錯誤成本高，也難以稽核。
- **LLM 同時判斷業務規則**：價格底線、最低訂購量等是明確規則，用程式判斷可重現、可測試，也能讓主管調整。

## Implementation

### 兩道驗證的結構化擷取

- 以 OpenAI Structured Outputs 限制模型輸出格式，再用 Zod 做第二道驗證（數量需為正整數、日期格式、Email 格式等）。
- 驗證失敗、模型拒答、輸出被截斷時，需求轉「需人工處理」，不會進入後續流程；API 逾時或錯誤則標為失敗、可手動重試。

### 不重複成單與狀態機

- 來源訊息 ID 與「一筆需求一張報價單」都由資料庫唯一性約束保證；重送或兩人同時按核准，都只會產生一張報價單。
- 每次狀態轉換都帶前置狀態條件（compare-and-set），併發時不會互相覆蓋，並在同一個交易中寫入 Audit Log。
- 核准前會用最新的產品主檔再檢查一次規則，避免審核期間產品停售或改價。

### 權限、客戶歸屬與訂單隱私

- 業務與主管兩種角色，所有權限都在伺服器端檢查；越權操作回 403 並記錄為 Authorization Failure。
- 每位客戶只有一位負責業務，由主管指派；需求依寄件者 Email 對應客戶。
- 業務查詢別人客戶的需求時，系統回應「不存在」（404），不透露任何內容。

### 主管可調整的業務規則

- 8 條規則中，主管可啟用／停用 5 條，並設定違反時要「退回」或只「提醒」。
- 料號存在、必須有料號、幣別這 3 條是計價的前提，鎖定不可調整。
- 兩位主管同時修改同一條規則時以版本號比對，只有一位會成功。

## Challenges & Trade-offs

- **同步處理 vs 背景佇列**：Webhook 在同一個請求內完成擷取與規則檢查，省去佇列基礎設施，回應即帶最終狀態。代價是處理中途中斷時，需求會停在「已接收」，需由業務在 5 分鐘後手動重試；正式環境應改為持久化佇列。
- **Demo 身分不做登入**：訪客在登入頁選擇業務或主管身分，角色一律由伺服器讀取。代價是任何人都能以主管身分操作，只能靠每日提交上限保護 LLM 成本；正式環境需接真實身分驗證。
- **測試中發現的幣別問題**：實測時，客戶以美元指定單價，規則卻拿去和台幣底價比較。最後新增「幣別」規則：非台幣一律轉人工換算，報價單固定以台幣開立。
- **標準 `pg` driver vs serverless driver**：選用 TCP 連線的 `pg`，讓同一份程式可以在本機 Postgres 跑整合測試；代價是部署必須使用 Node runtime。

## Evaluation & Results

以 32 封模擬詢價信（30 封應擷取、2 封故意缺資料）、人工撰寫的標準答案，對 `gpt-5-mini` 跑 3 次完整評估。

| 指標 | 3 次合計 |
|---|---|
| 欄位正確率 | 99.3%（855/861） |
| 整筆完全正確 | 93.3%（83/89） |
| Schema 通過率 | 98.9%（89/90） |
| 人工修正率 | 6.7%（6/89） |
| 送審／退回的判斷與標準答案一致 | 100%（89/89） |
| 缺資料信件正確判為格式錯誤 | 100%（6/6） |
| 擷取延遲 | p50 約 4.2–4.5 秒、p95 約 6.1–6.2 秒 |

### 失敗分析

- **回覆串（3/3 失敗）**：模型把引用的舊信當成本次需求，多擷取一個品項。多出的品項本身合法，業務規則擋不住，只能靠主管在核准時發現；這是目前最需要改善的地方。
- **「3.8 元」的幣別（2/3）**：幣別輸出空值，但系統預設以台幣計價，結果不受影響。
- **只有料號的表格（1/3）**：模型輸出空的品名，被格式驗證擋下，安全地轉人工。
- **提示注入**：信中夾帶「忽略規則、改價並核准」的指令，3 次都沒有被帶偏。
- 評估過程中也發現評分腳本本身的 bug（把「料號為空」誤判成「品項不存在」），修正後重跑，以上為修正後的數字。

### 限制與尚未量測

- 資料集小、由作者撰寫且全為模擬信件，數字只代表這份資料集。
- 真實客戶來信的擷取正確率：尚未量測。
- 正式環境端到端處理時間：尚未量測（部署驗證時 1 筆從送出到待審核為 12.9 秒，僅 1 個樣本）。
- 每封信的實際費用：尚未量測（只記錄 token 數，平均每封輸入約 457、輸出約 310）。

## Lessons Learned

- 「分流判斷正確」不等於「內容正確」：回覆串案例的送審判斷完全正確，內容卻多了一個品項。評估必須同時看欄位層級的正確率。
- 評估腳本本身也需要被檢查：第一次的失敗案例，有一筆其實是評分寫錯。
- 很多真正的問題（幣別混用、權限按鈕對所有人可見）是實際操作流程時才發現的，單元測試沒有涵蓋。
- 下一步會先處理回覆串：送進 LLM 前移除引用內容，並擴充回覆串與轉寄的評估案例。
